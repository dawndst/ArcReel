# Note → SVT 主归属与备选（强制业务规则）

每个逻辑章节对应一个 Note；上、中、下分段按既定章节归并规则算同一章。Note 的人工资料归组不改变章节身份，也不自动改变 SVT 归属。
每个完成拆分的 Note 必须且只能主归属于一个 SVT；多个 Note 可以共用同一个 SVT，因为一个主线关键事件可能跨多章展开。正式关系是 Note 多对一 SVT，绝不把同一 Note 的不同事件拆成多个正式 SVT。铺垫、过渡、背景内容也须随 Note 归属，不得只放 supporting_event_ids 后漏掉主归属。SVT 不等于集、场或镜。

先判断本章推进、铺垫或收束哪一个主线关键事件。续接同一目标/冲突时沿用 existing_id，不能逐章复制同名 SVT；同一人物不构成合并的充分依据。已明确归属的 Note 在分批处理时必须沿用该主归属，所有事件均归入其中。
每个 SVT 输出 title、summary（目标/阻力/行动/结果或未闭合状态）、event_ids、mainline_reason、status。只使用输入中可见事实，不推测后文，不使用小说外部常识。已知的 Note 主归属列在可续接SVT.note_ids 中，必须遵守。

## 爆点与爽点必须成对保存场面和台词
SVT 下可以累积多个爆点 climaxes；每个爆点必须同时包含：
- scene：爆点场面，写清触发、人物动作、冲突转折和可见结果；
- dialogue_ids：爆点场面中的关键原文台词ID，至少一个，系统保留原句与说话人；
- event_ids：支持该场面的事件；
- note_ids：上述场面和台词实际对应的来源 Note，不能标到其他章节；
- reason：该场面为什么构成爆点。
爽点 payoffs 使用同一结构，写清压力与兑现，不能把伏笔回收冒充爽点。
每项场面、台词和来源必须相互对应；不能把整个 SVT 的台词列表冒充每个爆点的台词。不得编造原文对白。当前原文不足以提取完整爆点时，不输出缺台词的爆点对象，不凑数；系统会把不足两个完整爆点的 SVT 标为待补全。未完结主线可以保持 open，后续 Note 继续累积爆点。

## Note 的多个 SVT 备选
每个 Note 可在 alternatives 中给出最多五个不同的候选方向，每项包含 existing_id（复用已存在 SVT；新方向填 null）、title、summary、reason。这里只是备选，不能因此在 svts 中再给本 Note 创建第二个主归属。
确有多种理解时列出多个备选，解释分别适合的主线归属；没有合理备选可为空，不凑数。不要把主归属本身重复列为备选。备选只引用当前可见 SVT，不借用未来章节。
最终主归属由人可调整；采用备选是替换，不是追加第二个主归属。AI 不自动合并 Note、不自动决定成片分集。

## 先全章判断，后分批补充
整章方向材料提供当前 Note 的整章概况、全部事件的有界分层索引及截至本章的已核实关联。先据此选择本章主要推进的目标与冲突，不能只用本批前几个事件决定主归属。本批事件只决定本次新增的事件依据和爆点；整章索引不是任意引用尚未提供 event_id 或台词 ID 的授权。
识别已有 SVT 时看目标、主要阻力、因果连续和是否已收束，不只看相同人名或相似标题。当前 Note 有多条支线时主归属仍唯一，其他合理主线解释列为备选；不因唯一主归属而遗漏支线事实。相关跨章理解只能使用截至当前 Note 已揭示的版本；其 uncertain 结论只用于提示疑点，不用于确认身份。
爆点完整度不是事实准确性：数量达标不构成审核通过，普通事件不强行升级为爆点。遵守现有场面＋台词＋来源成对规则；沉默动作和没有完整对白的关键场面继续保留在事件和场镜依据中，不因不符合完整爆点结构而丢失。

本批每个事件 ID（包括过渡、梦境、未判定性质和非主线事件）都必须列入该 Note 唯一主归属 SVT 的 event_ids；supporting_event_ids 仅是辅助索引，不能代替正式归属。管理归属不表示所有事件已经证实或属于同一现实因果链；摘要应区分主推进、旁支和未明性质，不能为统一归属编造因果。
