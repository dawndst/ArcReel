# ArcReel 小说理解与约束层评估

评估对象：ArcReel 上游提交 `7b4f781ab2c57d3d4dd1d0a15bdc5c427262f250`；旧工作台提交 `7d07a0b`。本评估基于源码、提示词与部署验证，未用同一本长篇小说完成两套系统的真实模型对照实验。

## 结论

采用 ArcReel 的生产流程和界面。不要整体移植旧工作台的理解系统；先补充阅读与审核 SKILL，再为经验证的缺口增加最小服务端保障。

ArcReel 在分集、脚本确认、资产引用、产物依赖和任务恢复上有更完整的工程机制。旧方案对全书事实、证据、人物变化与上下文持久化的建模更专门，但尚未完成真实长篇小说的全文验收，不能据此宣布理解质量更高。

## 代码证据与区别

| 维度 | ArcReel 已有机制 | 旧方案 | 判断 |
| --- | --- | --- | --- |
| 项目概述 | `ProjectManager._read_source_files` 默认最多 50,000 字符；生成 synopsis、genre、theme、world_setting | 分批读取全书，事实、摘要和检查点独立保存 | ArcReel 的默认概述不等于全书理解。旧方案目标更适合长篇，但需真实验收 |
| 分集 | 50,000 字符窗口；最近 5 个切出集的标题、钩子；原文锚定、连续范围与源文变更重映射 | 依赖累计拆解资料和改编要求生成分集 | 保留 ArcReel 分集实现；补全书背景，避免重做分集引擎 |
| 单集剧本 | 本集原文、项目概述、资产、当前与下集大纲、附加指令进入模型请求 | 注入按人物、场景和章节检索的世界事实及快照 | ArcReel 对局部制作足够明确，跨卷背景需额外供应 |
| 原文依据 | 分集锚定；drama 分镜 `source_text` 可为空；reference_video 单元原文锚有逐字子串校验 | 事实引用需定位到原文区间，区分叙述、人物说法、传闻、推断 | 两条 ArcReel 生成路线的溯源强度不同；引用存在也不能证明语义推断正确 |
| 人物变体 | 同一角色下衍生资产，支持少年、换装等；`本体/衍生` 可引用；衍生图编辑本体图 | 身份、年龄阶段、形态、状态分开，事实有剧情时间与揭示位置 | ArcReel 已能表示和选择多套外观。欠缺的是何时应使用哪套、变化是否有依据的语义约束 |
| 记忆 | 项目与用户 Markdown 记忆；索引有加载上限，详情按需读；文件原子写入，后写覆盖 | SQLite 原子事实、关系、分层摘要、调用日志、恢复检查点 | ArcReel 的笔记适合轻量创作；不能直接等价为可查询、带覆盖率的全书事实库 |
| 约束执行 | schema、资产引用、能力与时长检查、无效草稿隔离、脚本确认指纹、产物依赖 | 专门检查原著一致性、人物状态、图片审核与事实变化 | 保留 ArcReel 工程约束，仅补语义与证据的缺口 |
| 提示词替换 | 各项目物化独立 profile，保留用户修改；服务端文本生成另有模板与 instructions | 分阶段 SKILL 绑定、运行时冻结版本 | 独立 SKILL 有现成基础，但 SKILL 不等于所有模型请求的实际提示词 |

主要源码入口：

- [概述读取与生成](../lib/project/project_manager.py)：`_read_source_files`、`generate_overview`。概述读取按源目录文件名排序，并未复用分集的登记顺序读取器；后续修订需对齐源文入口，不能用提示词补回未读取的后文。
- [分集规划](../lib/episode/episode_planner.py)：`PLANNING_WINDOW_CHARS`、`_CONTEXT_EPISODES_LIMIT`、`_build_planning_prompt`。
- [剧本模型与原文锚](../lib/script/script_models.py)、[文本生成及校验](../server/text_generation.py)：`generate_drama_script_plan`、`collect_drama_violations`、`collect_reference_flat_violations`。
- [脚本实际提示词](../lib/prompts/prompt_templates/templates/text/drama_script_plan.md)、[新增与衍生资产规则](../lib/prompts/prompt_templates/templates/partials/shared/new_assets_rule.md)。
- [角色衍生资产](../lib/project/asset_derivatives.py)、[项目记忆](../lib/agent/agent_memory_store.py)、[记忆索引上限](../lib/agent/agent_memory_index.py)。
- [脚本确认](../lib/script/script_review.py)、[产物时新性](../lib/artifacts/artifact_currency.py)、[重启恢复](../lib/generation/restart_recovery.py)。

旧方案对照入口为 `workbench/server/world.py`、`book_memory.py`、`memory_journal.py`、`context_budget.py`、`variants.py`。其已知限制包括名称／别名检索的召回不足、模型上下文窗口依赖配置、保守而非精确 token 预算、重新通读时实体 ID 跨运行稳定性不足。旧方案也不能保证零遗漏。

## SKILL 能解决什么

可以先用独立 SKILL 改善以下创作行为，并利用原生项目记忆与资产：

1. 阅读前建立章节清单，分批读，记录已读范围与未解决问题；把全局背景、人物身份和外观变化分别保存，避免一份巨大摘要。
2. 审核称谓、身份与衣着的关系。“公子”不是富贵服饰的充分依据；外观应回到证据及当前剧情状态。
3. 发现年龄、变身、伤势或换装时建议对应衍生资产；使用资产名与衍生名，避免每集重新描述同一人物。
4. 对分集、剧本和图片增加一致性审核，给出具体问题、证据、影响对象及修订建议；不把生成说明、节奏评价当成疑点。
5. 在 Agent 调用生成工具时显式传递相关背景和改编决定，检查工具返回结果，不把“已经提醒模型”当成审核通过。

这些是提高概率和操作一致性的办法，不是完整性或不可绕过的保障。仅修改 `generate-script/SKILL.md`，不会让用户点击 Web 按钮触发的服务端模型自动读到该 SKILL。

## 哪些不能仅靠 SKILL

| 缺口 | 必要的确定性机制 |
| --- | --- |
| 声称已通读但实际漏章、源文改后仍沿用旧事实 | 源文清单与指纹、覆盖范围、可恢复检查点；完成状态由服务计算 |
| Web、MCP、Agent 使用的背景不同 | 在公共生成入口装配上下文，记录真实请求快照；不是仅在聊天中写提醒 |
| 引用不真实、冲突被新摘要覆盖 | 引用位置与文本校验、事实和冲突持久化、摘要保留依赖 |
| 不同剧情阶段误用同一形态 | 资产变体的有效范围及明确绑定；生成前检查绑定，语义不确定时提示 |
| 设定或图片已变化却仍算审核通过 | 图片内容指纹与设定版本绑定的人工确认记录，服务端在视频提交前检查 |
| 关键背景超出上下文预算 | 预算检查、按任务检索、明确遗漏与阻断；不能由固定窗口的 prompt 指令补救 |
| SKILL 替换后难以复现 | 为实际生成请求记录生效规则、模板版本和检索内容；项目文件独立不等于运行快照完整 |

若 SKILL 配套脚本或 MCP 工具实现这些机制，则可以交付为 SKILL 包，但真正提供保证的是脚本／服务和强制调用入口，而非 Markdown 指令本身。

## 建议的最小路线

先维持 ArcReel 原生生产流程。用一组覆盖跨年龄、兽形、受伤后恢复、晚揭示地域背景、同名人物和传闻误导的合成文本，比较“原生”和“增加阅读／约束／审核 SKILL”两种方案。

评价原文引用有效率、关键设定漏检、误用变体、提前泄露信息、人工修订量与调用成本。不能只比较文案是否通顺。

随后只实现三块经测试证明必要的基础能力：

1. 源文覆盖与带证据的故事资料；保留事实及状态，不强求一开始使用完整知识图谱或向量库。
2. 共享上下文装配；把故事资料与改编约束带到 ArcReel 的真实生成入口，并复用其产物依赖机制。
3. 确认与失效；绑定具体资产变体、图片和设定版本，在视频提交前执行检查。

完整复刻旧六阶段阅读流水线不是前置条件。图片人工确认的具体服务端缺口还需沿视频提交的全部入口专项核查，不能把原生“脚本确认”误当成已实现“图片与小说设定一致性确认”。
