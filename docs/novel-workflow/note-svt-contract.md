# Note、SVT、爆点的业务规则

此规则按用户确认的业务定义执行，替代“一个 Note 可主归属多个 SVT”的旧设计。

- 每个逻辑章节对应一个 Note。既定的上、中、下分段归并规则保持不变；人工合并 Note 只形成资料管理组合，原始章节 Note 不消失。
- 每个完成 SVT 拆分的 Note 必须且只能有一个主归属 SVT；多个 Note 可以共同叙述同一个主线事件，所以正式关系为 Note 多对一 SVT。
- 每个 Note 可以列出多个备选 SVT及推荐理由。备选不计入正式归属，人工采用备选是替换主归属，而不是追加第二个主归属。新方向和已有 SVT 都可以成为备选。
- 一个 SVT 累积多个爆点。每个完整爆点必须将爆点场面、原文台词、说话人、来源 Note 和原文依据放在同一条记录内。不能把 SVT 全局台词列表视为每个爆点的台词。
- 当前范围缺少对白时不编造原文台词；不足两个完整爆点时显示拆分待补全，不能标为完整。未完结事件可以继续开放，随以后 Note 追加爆点。多个主线解读不强行凑数，备选可以为空。
- 分批处理一章时不改变该章的主归属；背景和过渡内容也不能通过“辅助事件”逃避 Note 主归属。模型输出覆盖校验、一对一主键关系和跨批续接共同保证此约束。
- 规则文件为 `lib/novel_workflow/rules/svt.md`；项目专属版本为 `novel_workflow/rules/svt.md`。数据保存 `schema_version: 2`、`note_assignments`、`note_candidates`，爆点内保存 `scene`、`dialogues`、`note_ids`、`evidence`。
- 修改主归属会保存历史，整体迁移该 Note 的事件和爆点，保留其他 Note；受影响主线摘要需复核。跨 Note 的爆点不能被静默拆散。来源版本或候选过期时拒绝采用。

工作人员可从工作台左侧“规则与提示词”只读查看项目规则、生产模板、共享片段、Agent 技能和其他流程规则。该页显示实际模板文本、来源与内容指纹；运行时的小说内容、资产数据和 API 凭证不在其中。

## 问题回收与统一结论

阅读设置中的“问题回收与统一结论”默认开启，可独立关闭。泛读与跨章回查保留原始记录，另存每章结论版本；同章后文也可以回答前文问题。结论分为已解释、部分解释、剧情尚未揭晓、需要核对、结论冲突。章节导览和待查列表使用同一份结论，已解释项不再作为待查问题。工作人员可以查看引文并保存人工决定，再由 AI 更新导览；后续整理必须保留人工决定。

新回查任务先回收同章已解问题，再检索剩余问题，避免重复回读。每批回读一轮，仍未解决的问题留在结论中；已有完整且有效的回查报告可直接复用。结论材料共享人物身份、状态、事件和跨章关联的证据，不因分类不同而分别判断同一事实。不同说法分别判断，确认一条说法不等于确认某角色的全部说法。

SVT 仍是独立操作，不在回查后自动生成。提炼时使用整理后的导览和制作约束。正常悬念可以继续制作；只有改变人物身份、关键因果或对白归属且无法忠实呈现的冲突才阻断。结论、人工决定或对应规则变化后，旧 SVT 与场镜需要更新。部分解释仍按已知事实和未解部分分别呈现，不单独阻断；阻断仅针对需要核对或结论冲突。每条已解事实保留证据揭示位置，早于该位置的制作上下文不提前提供答案。

限制在阅读设置和任务区域显示：每任务默认最多100次模型生成，可设1–500次；包括结构修复，不含供应商内部网络重试，不等同美元费用上限。达到上限停止追加调用并保留已完成缓存，再次执行重新计数、复用有效缓存。每章结论输入最多16万字符，超出时明确报错而非截断。精简稿新材料最多按8个原文单元一批处理，已有2单元检查点继续复用。独立规则 `conclusions` 可在规则页面查看和替换。

## 性能实测与优化边界

2026-11-13 的一章旧流程实测（API 调用 757–796）共40次调用：泛读及逐段审核10次、模型耗时738.750秒；章节摘要3次、63.338秒；精简稿17次、184.909秒；回查及修复10次、125.107秒。模型耗时合计1112.104秒（18分32秒），首末调用跨度1159.771秒（19分20秒），模型耗时占95.89%。这是旧流程样本，不是当前完整新流程的性能承诺；新精简稿最多8单元批次、同章问题回收和有效缓存有望减少调用，但收益需用新任务验证，不能按批次扩大倍数推算整体加速。

同章场镜阶段的调用808–814共7次：两次初稿248.181秒、四次语义审核（含两次校验修复）41.365秒、一次详细镜头设计71.698秒。模型耗时合计361.244秒，首末调用跨度362.645秒，调用间本地处理约1.401秒；本样本主要瓶颈在串行模型调用与长输出。两个阶段之间的等待不计入执行耗时；供应商层的 `retry_count=0` 不代表没有应用层校验修复调用。

本次低风险修复跳过无变化审核建议、去除完全相同的重复建议，将无效位置、不匹配的修订前文字、无原文连续逐字依据的引文及同字段冲突建议隔离到待核实问题；其他有效建议仍可保留。隔离不等于认可建议或完成核对，工作人员仍需检查原文；待核实问题继续阻断组集，合法修订仍须通过原文证据校验。原始模型响应保留，不因这些局部无效建议重新生成整份审核。

当前暂不并发调用、不切换模型、不删除审核。后续可评估先由导演选镜，再为选中镜头补详细设计：目前 `complete_batch` 为全部镜头生成设计，组集也有设计完整性门槛。调整需要同步设计选择界面、生成状态、缓存和组集流程，本次不改；在这些约束明确并验证前，不承诺具体分钟数。
